# dsh-ask-chime

> A system alert the moment DeepSeek Harness needs you — or finishes the job.

English | [中文](README.md)

When an agent asks you a question, waits on an approval, or finishes a turn, you are usually not looking at the window. The first two wait for you indefinitely; the third you may not notice for a long while. None of them calls out. This plugin is those three sounds.

```
🔔 question  → the Windows chime, then a falling two-tone
🔔 approval  → the calendar notification, then a rising two-tone
✅ done      → print-complete, then a rising three-note arpeggio
```

Each alert has its own tone shape — falling, rising, climbing — so you can tell "it wants an answer" from "it is done" without looking.

## Where it hooks in

| Moment | Signal | Why it is enough |
| --- | --- | --- |
| A question | `ctx.userQuestions.ask()` | Both the `ask_user_question` tool and the plan review (`exit_plan_mode`) funnel through this **one** method, so wrapping it covers every prompt — including any question tool added later |
| An approval | `approval/request` | A waterfall dispatched only when the session policy actually reaches out to a human; a call the policy auto-denies stays silent |
| A finished turn | `agent/status` flipping `running` → `idle` | The same signal the web UI uses to decide whether a session is busy, so it means **the work stopped**, not "the reply ended". Only root agents chime, so a subagent settling mid-task never interrupts you |

The wrapper plays the sound and then delegates untouched, so the question itself is never affected. A failed sound (no player, muted machine, missing file) can never break the prompt or the turn it announced.

## Install

```sh
# install into a profile from GitHub (the package's cordis.patch.yml inserts the row)
dsh plugin --profile web add github:SwallowData/dsh-ask-chime
```

Then **restart DSH** — a profile's composition is expanded at startup.

For local development, point it at the checkout:

```sh
git clone https://github.com/SwallowData/dsh-ask-chime
dsh plugin --profile web add /path/to/dsh-ask-chime
```

## Configuration

The package ships its own `cordis.patch.yml` row. Override the same row in your profile's `cordis.patch.yml` to configure it:

```yaml
- insert:
    - id: ask-chime
      name: 'dsh-ask-chime'
      config:
        enabled: true                      # master switch
        questions: true                    # chime when you are asked something
        approvals: true                    # chime when an approval reaches you
        completed: true                    # chime when a turn finishes (root agents only)
        tones: true                        # Windows only: append the tone tail
        minTurnMs: 0                       # skip finished turns shorter than this (0 = always)
        questionSound: chimes.wav          # platform default, or an absolute path
        approvalSound: null                # null = platform default
        completedSound: null               # null = platform default
```

`minTurnMs` defaults to `0`, so every finished turn chimes. If "I asked one quick thing and it dinged" gets old, set it to e.g. `5000` and short turns go quiet — it is the one switch that only affects the finished-turn alert.

## Sounds

| Platform | Question | Approval | Done |
| --- | --- | --- | --- |
| Windows | `chimes.wav` + falling two-tone | `Windows Notify Calendar.wav` + rising two-tone | `Windows Print complete.wav` + rising three-tone |
| macOS | `Glass.aiff` | `Ping.aiff` | `Hero.aiff` |
| Linux | `dialog-question.oga` | `message.oga` | `complete.oga` |

Windows deliberately plays the wav first and then adds the tone tail: on a machine whose sound scheme maps notifications to "None" the wav still plays, and the tones are generated by the OS itself onto the default output device, so they cannot be missed.

## Platform support

- **Windows: verified.** Under a hidden, console-less spawn, both wav playback and `[console]::beep` work through the built-in `powershell.exe`.
- **macOS / Linux: implemented but untested** (`afplay`, then `paplay` / `pw-play` / `aplay`). PRs with real results are welcome.

## Design notes and trade-offs

- **Why wrapping `ask` at all**: DSH allows exactly **one** active `userQuestions` provider and the web client already owns it — there is no subscription seam left for a third-party plugin. So this wraps that one method, and does it carefully: it never double-wraps, it removes only its own layer on unload, and it will not clobber a wrapper installed after it.
- **Why not the harness shell service**: this plugin spawns one fixed command through `node:child_process` instead of `ctx.shell`. The shell service confines every execution with the deployment's sandbox policy, and an **agentless plugin call cannot be assumed to spawn under the default `workspace-write` policy** — measured on Windows, even `echo hello` exits 1 with no output, while the same command under an explicit policy works. The command built here is fixed, takes no input from the model or the session, and only makes a sound.
- **Why `agent/status` means "done"**: it is emitted only when the externally visible status actually changes, and `idle` means no turn is running; the web UI uses the same event to decide whether a session is busy. It is more precise than `agent/turn-stopping`, which only says the turn is about to close and cannot tell whether the agent immediately gets busy again. An interrupt or a turn error also lands on `idle`, so those chime too — they are finished as well.
- **Why subagents stay silent**: a subagent is an Agent too and emits the same event. Filtering through `agents.roots()` keeps it to root agents, otherwise one long task would ring several times as its children settle.
- **Failure is contained**: a missing player, a muted machine, or a missing sound file produces one warning and nothing else.
